## 1. 产品定位

ShopBGRemover 是面向电商卖家的批量商品图片处理工具，核心目标是让用户在一个工作区内完成：

1. 去除图片中的物体或水印
2. AI 去除图片背景
3. 添加透明、纯色或用户上传的背景
4. 调整商品位置、尺寸和画布
5. 按电商平台规范批量导出

重点支持的电商平台：

- Shopify
- Amazon
- eBay
- Temu
- Shopee
- TikTok Shop

产品不与综合设计软件正面竞争，核心差异化方向是：

- 电商商品图专用工作流
- 批量处理
- 多平台尺寸预设
- 批量命名与 ZIP 导出
- 本地去物体、去水印
- 用户上传背景模板
- 清晰透明的按次积分计费

#### 卡密生成和闲鱼发货流程

第一版采用人工发货，不依赖闲鱼 API：

1. 闲鱼用户拍下并完成付款
2. 管理员登录 ShopBGRemover 卡密管理后台
3. 选择 100、300 或 1000 积分卡
4. 输入闲鱼订单号或订单备注
5. 点击“生成并预留卡密”
6. 后台生成一张随机卡密并标记为 `reserved`
7. 明文卡密只显示一次
8. 管理员点击复制，通过闲鱼聊天发送给买家
9. 点击“已发货”，卡密状态变为 `delivered`
10. 买家登录 ShopBGRemover，在卡密充值页面完成兑换
11. 兑换成功后状态变为 `redeemed`

推荐按订单即时生成一张卡密，不建议一开始预生成大量明文卡密。这样可以降低：

- CSV 文件泄漏
- 同一卡密重复发给多个买家
- 无法判断卡密对应哪个闲鱼订单
- 卡密被内部或外部提前兑换

管理员卡密页面至少需要：

- 生成单张卡密
- 批量生成卡密
- 选择积分面额
- 填写闲鱼订单号
- 一键复制明文卡密
- 标记已发货
- 查看 `generated/reserved/delivered/redeemed/void/expired` 状态
- 按闲鱼订单号搜索
- 按卡密前缀和末四位搜索
- 查看兑换时间
- 查看兑换账号的脱敏信息
- 作废未兑换卡密
- 导出操作日志

卡密明文处理原则：

- 数据库只存哈希
- 单张即时生成时，明文只在生成结果中显示一次
- 管理员复制后通过闲鱼聊天发给买家
- 如果批量生成，则只允许下载一次 CSV
- CSV 应保存在安全位置，发完后及时删除
- 不得把完整卡密写入普通应用日志
- 闲鱼聊天记录可以作为发货凭证

建议的闲鱼发货文案：

```text
这是您购买的 ShopBGRemover 充值卡：

卡密：SBG-XXXX-XXXX-XXXX-XXXX
积分：300

使用方法：
1. 打开 https://www.shopbgremover.com
2. 登录您的账号
3. 进入“卡密充值”
4. 输入卡密；如有推荐人，请同时填写推荐码
5. 确认后积分立即到账

请勿将卡密转发给他人。卡密兑换后无法再次使用。
```

发货后的客服处理：

- 用户输入错误：根据订单号核对卡密前缀和末四位
- 卡密仍是 `delivered`：引导用户检查字符和登录账号
- 卡密已经由该用户兑换：展示到账时间和积分流水
- 卡密被其他账号提前兑换：冻结相关账号并进行安全调查，确认泄漏后补发新卡
- 未兑换订单退款：先将卡密标记为 `void`
- 已兑换订单争议：通过积分流水冲正，不能直接删除兑换记录

后续如果闲鱼存在稳定且合规的订单通知接口，可以再考虑自动发货；第一版不使用第三方自动发卡工具，避免账号权限、卡密泄漏和平台规则风险。

## 3. 拉新与推荐奖励

### 3.1 用户称呼

取消订阅制后，不再使用“正式会员”作为系统概念，统一使用：

- 付费用户
- 推荐人
- 被推荐用户
- 付费积分
- 奖励积分

### 3.2 推荐人资格

推荐人必须至少完成过一次真实充值。

### 3.3 推荐奖励

推荐关系只计算直接邀请，不做多级分销。

- 被推荐用户第一次充值后，推荐人获得其购买基础积分的 15%
- 被推荐用户后续充值，推荐人获得其购买基础积分的 10%
- 奖励只按实际购买的基础积分计算
- 赠送积分不参与再次计算
- 奖励为平台积分，不可提现、不可转让
- 推荐奖励积分有效期建议为 90 天

示例：

| 被推荐用户购买 | 首充推荐人奖励 | 后续充值推荐人奖励 |
|---|---:|---:|
| 100 积分 | 15 积分 | 10 积分 |
| 300 积分 | 45 积分 | 30 积分 |
| 1000 积分 | 150 积分 | 100 积分 |

### 3.4 被推荐用户首充奖励

已确认采用：

> 首次充值满 ¥60，额外赠送 30 积分。

采用满 ¥60 门槛的原因：

- 如果所有首充固定赠送 30 积分，100 积分包的首次实际单价会低于 300 积分包
- 会造成价格倒挂，推动用户只购买最小积分包
- 满 ¥60 赠送可以推动用户选择 300 积分包

### 3.5 推荐奖励风控

实施推荐系统时必须包含：

- 一个新用户只能绑定一个推荐人
- 推荐关系绑定后不可更改
- 同一设备、IP、支付账户不能互相邀请
- 推荐人必须是已充值用户
- 被推荐人必须是从未充值的新用户
- 退款、拒付和欺诈订单不产生奖励
- 已发奖励在退款或拒付时自动收回
- 余额不足时允许记录负奖励余额或冻结账户
- 异常大量邀请进入人工审核
- 推荐积分和付费积分分开记录
- 奖励只在支付成功后生成
- 订单号必须幂等，避免重复发放奖励

### 3.6 推荐系统技术方案

状态：🟡 推荐关系、奖励核心、卡密首次兑换绑定、推荐中心奖励明细、可用余额、有效期和脱敏邀请明细均已部署。真实生产闭环、待生效观察期和更完整设备/IP 风控尚未完成。

推荐系统沿用当前技术栈：

- Cloudflare Worker：处理推荐关系、支付回调和奖励发放
- Cloudflare D1：保存推荐关系、订单、积分批次和积分流水
- Google 登录：确认推荐人和被推荐用户身份
- PayPal：确认真实充值、退款、拒付和争议

#### 推荐链接

每个用户生成一个不可连续猜测的随机推荐码，例如：

```text
https://www.shopbgremover.com/?ref=K7M4P9Q2
```

推荐码可以提前生成，但只有完成过至少一次充值的用户才具备奖励资格。

推荐链接进入网站后：

1. 后端验证推荐码有效
2. 写入经过签名的第一方 `referral_pending` Cookie
3. Cookie 建议保留 30 天
4. 第一次记录后锁定，不被后续推荐链接覆盖
5. Google 登录回调时把推荐关系绑定到新账号
6. 已经存在的老账号不再绑定推荐人

不得只依赖前端 `localStorage` 保存推荐码，否则用户更换浏览器、跳转登录或清理数据时容易丢失，也容易被篡改。

#### 推荐关系绑定

推荐关系在新用户第一次注册时绑定，不等到支付时才临时绑定。

绑定时检查：

- 被推荐用户是新注册账号
- 推荐人存在
- 推荐人和被推荐人不是同一个用户
- 被推荐用户还没有推荐人
- 推荐码没有被禁用
- 推荐人的付费资格可以在首次支付奖励前再次验证

推荐关系一旦绑定，不允许用户自行修改。

#### 首次充值处理

以用户购买 300 积分包为例：

1. PayPal 确认订单支付成功
2. 锁定并验证订单尚未处理
3. 给购买者发放 300 付费积分
4. 因订单金额达到 ¥60，给购买者发放 30 首充推广积分
5. 检查购买者是否存在有效推荐人
6. 检查该订单是否为第一笔有效充值
7. 给推荐人发放 `300 × 15% = 45` 推荐积分
8. 写入三条独立积分流水
9. 将订单、推荐关系和奖励状态一次性标记完成

建议的幂等键：

```text
purchase:{order_id}:buyer
first-purchase:{order_id}:invitee
first-referral:{order_id}:referrer
```

#### 后续充值处理

后续充值只对实际购买的基础积分计算 10%：

```text
repeat-referral:{order_id}:referrer
```

以下项目不产生推荐奖励：

- 免费注册积分
- 首充赠送积分
- 推荐人获得的奖励积分
- 客服补偿积分
- 活动赠送积分
- 退款后重新补发的非付费积分

#### 并发和重复回调

支付页面回调、用户重复点击和 PayPal Webhook 可能同时到达。

必须使用：

- 订单状态条件更新
- D1 原子批处理/事务
- 积分流水唯一幂等键
- PayPal Capture ID 唯一约束

任何一个订单无论收到多少次回调，都只能：

- 给购买者发放一次积分
- 给被推荐用户发放一次首充奖励
- 给推荐人发放一次 15% 或 10% 奖励

#### PayPal Webhook

不能只依赖浏览器支付完成回调，还需要接入 PayPal Webhook：

- 支付完成
- 退款
- 拒付
- 争议
- 撤销

Webhook 必须验证 PayPal 签名，并使用 PayPal 事件 ID 做幂等处理。

推荐人的奖励积分建议先显示为“待生效”，在退款期限结束后转为可用；如果选择立即可用，则退款时必须支持：

- 收回剩余奖励积分
- 余额不足时产生负奖励余额
- 冻结继续处理和提现类操作

#### 反作弊判定

优先使用强关联信号：

- PayPal Payer ID
- 相同支付账户
- 相同 Capture 付款来源

辅助使用：

- IP 哈希
- 设备标识哈希
- 浏览器特征
- 注册时间
- 充值时间
- 邀请频率

不能仅凭相同 IP 直接封禁，因为家庭、办公室和公共网络可能共享 IP。相同支付账户互相邀请应直接拒绝，其他信号采用风险评分和人工审核。

#### 推荐中心界面

付费用户看到：

- 推荐码
- 一键复制推荐链接
- 已邀请注册人数
- 已完成首充人数
- 待生效奖励积分
- 可用奖励积分
- 历史奖励流水
- 奖励规则和有效期

被推荐用户看到：

- 推荐关系已记录
- 首次充值满 ¥60 赠送 30 积分
- 当前订单预计获得的积分

#### 推荐系统验收标准

- 老用户不能被重新绑定推荐人
- 同一新用户只能绑定一个推荐人
- 用户不能推荐自己
- 相同支付账户不能获得推荐奖励
- 首笔有效订单只发 15%
- 后续有效订单只发 10%
- 赠送积分不参与奖励计算
- 重复支付回调不重复发积分
- 退款和拒付可以完整冲正
- 所有积分变化都有可审计流水

### 3.7 充值卡绑定推荐关系

充值卡页面增加推荐码输入框：

```text
卡密：      [ SBG-....                ]
推荐码：    [ K7M4P9Q2（如有）       ]
```

推荐关系可以在以下两个时间点之一绑定：

1. 新用户通过推荐链接注册时
2. 尚未充值且尚未绑定推荐人的用户，第一次成功兑换充值卡时

以最先成功发生的绑定为准，之后不可修改。

充值卡推荐规则：

- 用户必须登录后兑换
- 推荐码可以不填，但不填则不会获得被推荐用户首充奖励
- 如果填写推荐码，必须验证推荐人存在且具备付费推荐资格
- 推荐人和兑换者不能是同一个账号
- 如果推荐码错误，整个兑换失败，卡密保持未使用
- 如果用户已经绑定推荐人，页面不再允许修改，只显示已绑定状态
- 如果用户已经完成过任何充值，即使没有推荐人，也不能再补填推荐码
- 用户不填推荐码时，提交前提示充值后无法补填

确认提示：

> 本次未填写推荐码。充值成功后将不能再补填推荐人，也不会获得被推荐用户首充奖励。是否继续？

只有同时满足以下条件，被推荐用户才获得 30 积分：

- 存在有效推荐关系
- 这是被推荐用户第一笔有效充值
- 购买或兑换的基础积分不少于 300 积分
- 对应金额达到 ¥60

卡密首充示例：

用户 B 输入一张 300 积分卡，并填写用户 A 的有效推荐码：

1. 验证卡密有效且未使用
2. 验证 B 从未充值且未绑定推荐人
3. 验证 A 是有效付费推荐人
4. 将 A 和 B 的推荐关系绑定
5. 标记卡密已由 B 兑换
6. 创建一笔 `voucher` 内部订单
7. 给 B 发放 300 付费积分
8. 给 B 发放 30 首充推广积分
9. 给 A 发放 `300 × 15% = 45` 推荐积分
10. 写入订单、卡密、推荐关系和三笔积分流水

上述步骤必须在同一个 D1 原子批处理/事务中完成。

建议幂等键：

```text
voucher:{voucher_card_id}:buyer
voucher-first:{voucher_card_id}:invitee
voucher-referral:{voucher_card_id}:referrer
```

如果 B 以后继续兑换 1000 积分卡：

- B 获得 1000 付费积分
- A 获得 `1000 × 10% = 100` 推荐积分
- B 不再获得 30 首充积分

充值卡没有 PayPal Payer ID，因此自我邀请风控需要更加严格：

- 相同设备直接进入高风险
- 短时间相同 IP 注册、绑定和兑换进入高风险
- 同一推荐人短时间出现大量卡密兑换进入人工审核
- 推荐奖励可以先进入“待生效”
- 闲鱼订单确认或观察期结束后再转为可用
- 卡密批次、闲鱼订单号可作为后台备注，便于争议核对

## 5. 图片处理工作流

目标工作区采用明确的三步流程。

### 第一步：去物体或去水印

状态：已确认，尚未实施。

规则：

- 用户主动选择是否开启
- 浏览器本地处理
- 不调用 AI API
- 不扣积分
- 支持矩形框选
- 支持笔刷涂抹
- 笔刷粗细可调
- 支持撤销、重做和清空选区
- 应提供处理前后预览

处理顺序：

- 多余物体位于背景，并且用户准备 AI 去背景：通常无需额外处理
- 多余物体位于商品主体：先去物体，再进行 AI 去背景
- 多余物体位于主体边缘：可能影响透明边缘，需要重点测试

本地实现方向参考：

- 参考目录：`~/code/ecomsellerkit/ecomsellerkit/`
- 参考模块：Product Photo Cleaner
- 基础实现可使用局部修复/Inpainting
- 优先考虑基于邻近像素的 Telea、Navier-Stokes 或 PatchMatch 类方法
- 不调用外部 AI 服务

### 第二步：AI 去背景

状态：现有 AI 去背景已上线，目标计费开关和新流程尚未实施。

工作区需要增加明确开关：

> AI 去除背景
> 使用 AI 处理，成功后每张扣除 1 积分

规则：

- 勾选开关只表示用户授权调用，不立即扣积分
- API 成功并返回有效结果后才扣 1 积分
- API 失败不扣积分
- 下载不扣积分
- ZIP 下载不扣积分
- 更换背景不扣积分
- 调整尺寸不扣积分
- 重复导出不扣积分
- 原图是有效透明 PNG 时，可以跳过去背景且不扣积分
- 批量处理只对实际调用 AI 的图片扣积分
- 用户可以逐张取消 AI 去背景

处理前必须显示：

> 本次共 12 张图片，其中 10 张需要 AI 去背景，预计扣除 10 积分。

重新调用规则：

- 网络重试不得重复扣积分
- 同一个处理任务必须使用唯一任务 ID
- 已完成任务应优先恢复原结果，不重新调用 API
- 用户修改原始清理结果并要求重新去背景时，属于新任务
- 新任务再次扣积分前必须明确提醒用户

提醒文案：

> 当前图片已经完成 AI 去背景。重新处理将再次扣除 1 积分，是否继续？

### 第三步：添加背景并导出

状态：已确认，尚未实施。

这一版只实现用户上传背景模板，不调用 AI 生成背景。

背景选项：

- 透明背景
- 纯白背景
- 自定义纯色
- 用户上传背景图
- 保留原背景

用户上传背景图后支持：

- 填满并裁切
- 完整显示
- 拉伸
- 背景缩放
- 背景移动
- 商品缩放
- 商品水平移动
- 商品垂直移动
- 商品居中
- 商品底部对齐
- 商品占画布比例
- 简单商品阴影
- 背景模糊
- 批量应用到全部图片
- 单张图片单独覆盖设置

默认背景适配方式：

> 填满并裁切

不要默认拉伸背景，避免背景图片变形。

### 5.1 背景功能依赖关系

- 原图包含有效透明通道：可直接添加背景，不扣积分
- 原图没有透明通道：需要先完成 AI 去背景
- 未获得透明主体时，应禁用背景替换并解释原因
- 不得因为用户上传背景图而自动调用 AI 或自动扣积分
- 只使用去物体、去水印时，允许直接导出修复后的原图

提示文案：

> 当前图片没有透明背景。请先开启 AI 去背景（成功后扣除 1 积分），或者上传带透明通道的 PNG 图片。

### 5.2 本版背景模板范围

MVP 图层结构：

```text
用户上传的背景图
        ↓
透明商品主体
        ↓
目标平台尺寸画布
        ↓
PNG / JPEG / WebP 导出
```

背景模板优先保存在浏览器本地，不上传服务器。

后续版本再考虑：

- AI 生成背景
- 在线背景模板库
- Logo 层
- 前景装饰覆盖层
- 多图层模板
- 团队模板共享
- AI 自动匹配商品和背景

AI 生成背景未来需要单独定义积分价格，不能包含在 1 积分去背景中。

## 10. 踩坑记录

### 10.1 Download ZIP 重复处理

- 现象：图片已经处理完成，点击 Download ZIP 后，前端再次执行图片处理流程
- 风险：重复调用 fal.ai、重复消耗API余额，甚至重复扣用户积分
- 处理：已修复并部署
- 长期原则：下载只能读取已经存在的结果，禁止触发处理函数

### 10.2 fal.ai 余额显示有延迟和取整

- 现象：处理少量图片后，后台余额没有立即变化
- 原因：fal.ai 页面提示余额更新可能延迟，界面只显示到美分
- 影响：不能通过一两张图片精确计算单价
- 处理：使用较大批次累计差额估算
- 财务原则：内部成本按 ¥0.015/张保守核算

### 10.3 免费额度文案和后端不一致

- 后端实际游客累计 10 张
- 注册实际赠送 20 积分
- 页面出现每天 3 张、注册赠送 5/10/20 张等多个版本
- 风险：用户投诉、计费争议、条款不一致
- 处理状态：待新积分体系实施时统一修复

### 10.4 固定首充赠送 30 积分导致价格倒挂

- 100 积分包首充后为 130 积分，实际约 ¥0.169/张
- 300 积分包首充后为 330 积分，实际约 ¥0.182/张
- 结果：小包比中包单价更低
- 调整：改为首次充值满 ¥60 赠送 30 积分

### 10.5 背景替换不能隐式触发收费

- 用户上传背景不等于同意调用 AI
- 无透明主体时必须提示用户选择 AI 去背景
- 不允许自动调用和自动扣积分

### 10.6 本地清理和 AI 去背景的顺序

- 主体上的物体或水印应先清理，再进行 AI 去背景
- 如果 AI 去背景后再修改原始清理结果，可能需要重新生成透明边缘
- 重新调用 AI 前必须明确提示再次扣 1 积分

### 10.7 奖励积分不能与付费积分混账

- 付费积分永久有效
- 免费积分和推荐积分有有效期
- 退款时需要撤销奖励
- 必须分账才能正确处理过期、退款和消费优先级

### 10.8 当前支付回调存在并发重复加积分风险

- 当前实现先查询订单状态，再分别增加积分和更新订单状态
- 两个并发请求可能同时读到 `pending`
- 如果同时继续执行，理论上可能重复增加购买积分
- 当前捕获接口只按订单 ID 查询，没有同时验证订单属于当前登录用户
- 推荐奖励上线后，15% 和 10% 奖励也会面临相同风险
- 调整要求：订单归属验证、订单条件更新、D1 原子批处理、积分流水唯一幂等键、PayPal Capture ID 唯一约束必须一起实施

### 10.9 卡密兑换不能分步骤提交

- 不能先标记卡密使用，再单独发放积分
- 不能先绑定推荐人，再单独验证卡密
- 任一步失败都可能造成卡密已使用但用户没有积分，或者推荐奖励重复发放
- 卡密状态、内部订单、推荐关系和积分流水必须在同一个原子操作中提交

### 10.10 卡密渠道缺少统一支付身份

- PayPal 可以使用 Payer ID 辅助识别自我邀请
- 闲鱼卡密兑换无法自动获得买家的统一支付身份
- 需要结合设备、IP、兑换时间、推荐频率和闲鱼订单备注进行风控
- 不应仅凭共享 IP 直接封禁正常用户

### 10.11 填错推荐码不能消耗卡密

- 推荐码校验必须发生在卡密最终核销之前
- 推荐码无效时整个兑换回滚
- 卡密仍保持原来的 `delivered` 状态
- 避免用户因输入错误损失充值卡

### 10.12 大量预生成明文卡密存在泄漏风险

- 批量 CSV 一旦泄漏，任何人都可以抢先兑换
- 同一张卡密可能被人工重复发送
- 很难追踪卡密对应的闲鱼订单
- 第一版优先按订单即时生成单张卡密
- 数据库只保存哈希，明文只显示或导出一次

### 10.13 生产迁移与 Git 记录脱节

- 生产 D1 的 `d1_migrations` 已记录两条 2026-06-22 迁移
- 仓库中原先不存在对应 SQL，也没有迁移目录
- 不能根据最终表结构伪造历史迁移并直接重放到生产
- 处理：保存最终生产 schema 基线和历史迁移元数据；未来迁移从 `0003` 开始

- `.vercel/output` 中包含生成后的静态文件和构建产物
- 风险：工作区每次运行工具都会产生无关修改，也可能把本地状态误当成生产来源
- 处理：从 Git 索引移除并加入 `.gitignore`，本机文件不删除

- 本次不以强制升级或 `npm audit fix --force` 破坏旧路径；后续应删除不再使用的 Next 部署链，或先制定迁移方案再升级

### 10.18 中国大陆 PayPal 账户之间不能互付

- PayPal 中国官方帮助说明，中国大陆账户目前只能向中国大陆以外注册的 PayPal 账户发送国际付款
- 当前 ShopBG Remover 收款账户属于中国大陆区，因此中国大陆区 PayPal 买家不能用 PayPal 向该账户付款
- 处理：中国大陆普通买家继续使用闲鱼人民币付款和卡密兑换；PayPal 网站结账面向中国大陆以外的买家
- 真实 PayPal 捕获/退款测试需要使用非中国大陆区且不属于收款商户本人的买家账户

### 10.19 推荐首触点不能被后续链接覆盖

- 首版实现检查时发现，如果每次访问 `?ref=` 都重写 Cookie，用户的推荐归属会被后续链接抢占
- 处理：后端优先验证已有签名 Cookie；只要首个 Cookie 仍有效且推荐码未禁用，后续推荐链接只能返回 `already_captured`，不能覆盖
- 前端不在 `localStorage` 保存推荐归属；关系只由后端签名 Cookie和 D1 唯一约束确定

### 10.20 两笔并发订单可能同时被误判为首充

- 如果两个不同订单同时完成，单纯在事务外查询“是否存在历史订单”，两个请求都可能看到没有首充
- 处理：增加用户维度的部分唯一索引，最多允许一个订单的 `is_first_qualified_purchase=1`
- 捕获或卡密批处理发生首充索引竞争时，失败事务会重新读取订单状态并再计算一次；另一笔自动降级为 10% 后续奖励
- 自动化测试使用两个 300 积分订单并发完成，结果固定为一笔首充、一笔后续、一次 30 积分赠送，推荐人总奖励 75

### 10.21 卡密推荐绑定不能先写关系再核销卡密

- 如果先创建推荐关系，再单独核销卡密，填错卡密、并发抢兑或后续 SQL 失败会留下没有有效订单的推荐绑定
- 处理：先在内存中验证推荐码、推荐人付费资格和兑换者首充资格；推荐关系 INSERT 与卡密核销、内部订单、三类积分和成功尝试记录在同一个 D1 批处理中
- 推荐码错误、推荐人未充值、本人推荐、已有不同推荐人或兑换者已有充值时，整个请求在核销卡密前失败
- 自动化测试确认无效推荐码后卡密仍为 `generated`、订单和推荐关系均为 0、余额不变
